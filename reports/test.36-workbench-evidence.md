# test.36：默认工作台内容存证与历史重试

日期：2026-09-13。应用 `0.1.9-test.36+41`，审计／工作台宿主 test.36；核心 crate test.22、内容格式 7，运行时／SDK crate test.11，默认工作台 guest test.13，随包清单 test.36。第一方 AGPL-3.0-only。仅本地开发，无远程推送、标签、Release 或上传。

## 默认应用实现

工作台 create／apply 实际调用 Pool.record_transform，创建、编辑、收藏、阶段、删除／恢复等现有内容操作将原始任务观察与最终内容通过核心 with_evidence 接口同事务保存。无关查询仍不生成持久证据。错误任务、错误输出、提交前授权失败或崩溃均不能留下新内容与孤立证据。实际内容权限仍由当前连接、包批准、对象范围和时限控制。

新增核心宿主本地 Store::operation_commit，按卡片和操作核对原始提交，SQL 先检查长度，再验证原命令、身份、回执和证据引用。不存在、其他卡片或非内容操作返回 None，损坏返回错误；未添加 guest 任意读取权限或新存储格式。

已提交重试先核对全局操作 ID 与原始 Request。创建比较原始草稿；编辑比较 action、proposed、text、flag 和原 expected_revision，沿用历史宿主 current／now，不拿插件规范化后的输出冒充用户意图。匹配后复用原 command 和同一证据，通过当前授权再次进入核心幂等路径，不重新运行插件，不更新 undo 截止时间，也不覆盖后续内容修订；返回原操作的业务结果及历史 revision，而不是当前最新内容。

显式更换并启用新包后也可核对旧操作，但旧证据不赋予执行权限。不同请求、跨卡操作 ID、不同基准修订或没有受支持原始意图的旧操作均拒绝；未提交的新操作仍使用现有 CAS 与实际执行路径。当前只恢复已提交意图，不持久保存尚未提交的用户操作、撤销窗口或临时附件授权。

## 发现与修正

完整故障回归发现旧 auditing 测试在 finish 已关闭实例池后仍期待“清除封存失败并刷新”自动恢复写入。这与当前显式重新启用的生命周期规则冲突。已改为验证存储故障解除后会话仍只读，只有 configure_plugin 显式启用才恢复写入；未弱化生产隔离、修改已提交内容或让刷新复活旧连接。首次失败保留在日志中，修正后对应测试通过。

首次审计组包含1100次实际创建、封存、只读检查和重开，组耗时139.65秒；其持续写入场景通过，但同组另一个旧断言失败。该时间不是单次任务延迟或纯写入耗时，而且期间有并行编译。相比此前不存证的历史组，当前大包重复保存与反复完整性检查的开销明显，需要后续实测优化，不能宣称性能已完成。

- 后续采用一份历史包配有序任务集合的版本化批量证据，并固定整个设置意图、分页顺序、基准修订和宿主投影版本；每页与总执行预算同时受控，全部成功后一次原子提交。不能截断证据、只保存前16页或将一次设置保存拆成多个内容事务。
