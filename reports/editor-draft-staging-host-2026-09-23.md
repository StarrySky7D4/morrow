# 宿主持久附件导入与可恢复清理

日期：2026-09-23。当前仍为 ddd9cc8eec224af51f4e58654c9b297332147d96 上的本地工作树，应用 0.1.9-test.54+58、第一方插件 0.1.9-test.54.3 不变。没有提交、推送或发布。

## 问题与本轮范围

旧附件导入只把字节放入 Core，再把草稿归属保存在进程内；退出后，未选入草稿的附件没有可恢复的导入身份。Core 原子暂存原语已在上一阶段完成，本轮把固定业务提案、独立暂存状态与可释放归属接入宿主 Rust 库。旧私有传输和 Dart 导入接口尚未切换，不能宣称主界面已经具备此项恢复能力。

## 已实现的行为

- 每个草稿使用独立、仅含元数据的私有审计记录，和正文草稿拥有不同修订。先记录 Pending 和容量预留，再读字节；Core 同事务保存字节和 Snapshot owner，随后记录 Ready。未选字节不挂到私有记录的 CardRecord attachments，避免引入永久 event_blobs 引用。
- 请求固定卡片、草稿、原操作、正文基线代次、名称、类别、长度和 SHA-256。附件逻辑身份及 owner 由完整作用域和原操作派生，同字节可物理去重，但不同草稿/操作不能相互认领。
- 查询、列表和原操作核对不自动重开原文件或完成业务。相同请求重试优先核对持久记录：已保留原字节则不读取 reader，即使原文件已删除或正文已推进一代；未保留字节而正文代次已改变则拒绝重新读入。Ready、已消费或已放弃的原操作只返回历史关联和当前状态，不重新导入。
- 主草稿保存把选定附件引用与 consumed_imports 在同一核心事务中提交。后续清理失败不能把已经成功的正文提交改报为未提交。下一次正文更新前先处理上一代清理义务；清理失败时保留原代次、标记和附件，拒绝依赖它的新代次。
- 消费或整份草稿放弃后，导入立即失去可选资格；之后按顺序记录 Retired、释放 Snapshot、记录 Pruned。释放失败仍保留归属；释放成功而 Pruned 失败仍保留待清理条目和配额。重开只读，明确清理后才能移除条目。
- 显式放弃使用客户端固定 abandonOperation 和独立审计意图 kind 4；自动 Retired 使用内部确定性操作和 kind 2。修复了两种操作可能共用历史回执判断的问题，并拒绝客户端冒用内部操作前缀。
- 清理前核对原 Pending 提案与消费标记对应的精确附件。Ready 丢失 Snapshot 时停止清理，不掩盖损坏；已经 Retired 且 Snapshot 已释放则允许继续 Prune。普通正文保存不会为完全无关、未待清理的导入重复读取整份附件字节。

## 配额与保留边界

暂存最多每草稿 20 个当前条目、全库 320 个当前条目、64 MiB 声明字节预留、每记录 1 MiB 元数据、256 个记录身份，每记录 256 次修订。Pending、Ready、尚未 Prune 的 Retired 都计费。新 Pending 接纳前为已存在及新条目预留 Ready/Retired/Pruned 的修订余量，不能在接纳后才发现无法清理。

这是测试阶段的有限历史准入门槛，不代表长期历史维护已完成。到上限时明确拒绝新导入，不能通过自动换草稿或操作身份绕过审计。正文草稿、正式卡片及历史附件仍按原保留规则保护；Snapshot 释放只移除临时归属，物理回收继续遵守既有宽限和其他引用检查。

## 下一阶段

默认编辑自动保存、来源交接与富捕获、长期历史维护、语言/字体在途提案、正式迁移入口、完整 ErrorEnvelope、远端 Unknown 及 SDK/平台资格继续开放；本轮没有将整份深度审查标记完成。
