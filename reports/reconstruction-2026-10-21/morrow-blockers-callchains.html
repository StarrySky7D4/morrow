关键缺口：检查对象、调用者和实际访问掩码没有完全对齐

对象 / 操作已检查内容不能据此证明的内容
创建前 launch-token 对象capture_token_security() 通过 GetKernelObjectSecurity 读取其对象 DACL 与 label。R 创建后的实际 primary-token 对象具有相同对象安全描述符。
TokenDefaultDacl精确默认模板；允许项当前为 READ_CONTROL。它用于后续对象创建。该模板就是 token 对象本身的 DACL，或可以直接放入 token 专属访问位。
C 创建 R 后 readback检查 R 的进程/线程 SD；以 READ_CONTROL | TOKEN_QUERY（0x20008）打开 R token，读取 token facts 与 default DACL。实际 R token-object 的 DACL/MIC 满足 R 自开要求，以及 R 调用者具有 TOKEN_DUPLICATE 权限。
R 打开自己的 token请求 TOKEN_QUERY | TOKEN_DUPLICATE（0xA）；当前在此被拒绝。C 能查询此 token，就等价于 R 能以另一个掩码打开它。

Microsoft 文档确认，OpenProcessToken 的访问请求按 token 对象自身的 DACL 判断；TokenDefaultDacl 是新对象的默认 ACL 模板。因此，将创建前对象检查、默认模板检查、创建后实际对象检查分开，是必要的工程约束。

源码：创建前对象检查、创建后 readback、默认模板边界。官方：OpenProcessToken；TOKEN_DEFAULT_DACL。

phase016 是候选机制证据

独立探针观察到新进程实际 primary-token 对象 DACL 反映 launch TokenDefaultDacl，并不同于创建前对象；实验性初始化后只证明父进程的 query/duplicate 读取成功，受限子进程仍以 0xC0000142 在 main 报告前退出。这不能当作 case014 的因果证明，也不能当作产品 L1 已修复。新初始化方案尚未进入产品。

Windows API 文档对进程/线程默认安全描述符的说明，也不等于对新 primary-token 对象来源的通用保证。应保留“该 fixture 观察到”的限定。

推荐的下一步

  1. 在新独立 case 的既有 C post-create readback 窗口，记录实际 R primary-token 对象的 owner、DACL、MIC、原调用者上下文及请求掩码，并与同次 R 认证失败关联。
  2. 先证明拒绝条件，再为实际对象设计类型专用的 token-access 契约和生命周期；保留最小权限与精确 LogonSID。
  3. 先贯通 R 内部令牌准备与业务子进程启动并收到 SpawnReady，再验证业务结果、join、ACK、factory 退役和 account/setup 收尾。

不建议直接扩大通用 TokenDefaultDacl：源码已指出 token 的 QUERY 位与线程 GET_CONTEXT 位值重合，通用模板中的一个数值会产生不同对象语义。上述步骤是后续实施建议，本次没有恢复已暂停的验收。

05

资源退役链：局部关闭不足以释放整条尝试

正常清理已经有真实结构：业务完成与 native ACK、formal worker join、暂存原 runtime、protected owner finish/flush、scheduler shutdown、native threads 等待与 checked close、execution.retire_factory，最后生成原次清理准入，进入 account/setup 收尾。最新修正使原 protected owner 能在 scheduler 实际 shutdown 前完成。问题在于干净拒绝路径尚未覆盖整条所有权链。

事实当前语义应避免的推导
RunnerDispatch::RejectedR 创建 API 明确返回拒绝，且观察未丢失。拒绝发生过，因此所有资源都已经关闭。
LocalResources::Closed本层已拥有的资源关闭。registry、SDK、factory、账户及 setup 也全部退役。
policy_clean=true临时权限配置由原 owner 恢复，原 policy handles 有关闭记录。case_clean=true 或已签发令牌不再有任何活跃义务。
Unknown / observation_lost保留原 owner 与事实，不能由迟到结果自动重分类。重新提交同一 case、换 operation 或直接删除 ledger 就能恢复。
context settleresources clean、authority retired、要求的 join 均成立才移除 ledger 项。caller drop 等价于 settle；drop 实际只是 park。

原生 execution registry 和 agent context 各存在 16 的边界。若“确实干净拒绝”的证明无法跨层消费，安全保留策略会变成可用性限制。这里能确认的是有界容量与未闭合合同；尚无本次实测证明“第 17 次必然失败”，不能这样表述。

建议的完整修复单位：为同一尝试贯通 native、registry、SDK、factory、account/setup 的事实凭证，最终只有一个消费出口归还额度；确定干净的拒绝可以释放，Unknown 继续保留。验收同时覆盖正常完成和连续超过 16 次干净拒绝。

正常 owner/factory 收尾顺序；factory retirement 边界；独立结果维度；park 与 settle；P2/P3 剩余项。

B3 · 重启后缺少重新授权的可编辑恢复

EditorDraftReview 明确不携带 live capture、replay grant、draft owner 或业务 ACK 权限。retainedEditorDraft() 只能取回仍在本客户端 _draftOwners 中的原 owner。客户端重启后，持久 journal 可以还原内容和导出证据，但不能生成当下有效的编辑能力。

需要补的是“核对当前卡片版本 → 建立新的 capture authority → 绑定原持久证据与新 successor → 处理冲突/双活 → 继续编辑”的协议。简单序列化、反序列化旧 owner 或 scope 字符串无法完成这一授权转换。

Review 权限边界；原 live owner 发现；正式恢复 UI 分派。

B4a · 退役前读取失败可使 live owner 无法继续

这是本轮从源码推导的具体失败路径，未运行故障注入：

顺序源码行为已知结果
1_run → _reserveOwner同步冻结 session，暂停自动保存并阻止新 view/import/commit。
2await _control.read(...)此时 discard 尚未发送。
3只读失败或返回不匹配_dispatched=false；start() 已缓存失败 future。
4用户再次尝试root 仍返回缓存的同一个 attempt；start 不重做预检，inspect 又拒绝“没有已提交的原退役”。
5原 owner没有对应的未发送阶段释放 reservation 或重新核对入口，当前对象可能持续冻结。

应新增受原 reservation 和 generation 约束的“确定未发送”恢复分支：可重新做只读核对，或在确认原状态未改变时取消本地预留。已经发送 mutation 的 Unknown 则继续保留原身份，不能复用此分支解冻或重放。现有数据保留设计有价值，缺的是区分两种状态之后的推进能力。

reserve/read/dispatch 与缓存；reservation 冻结；root 缓存原 attempt。

B4b · successor、ACK、close 失败阶段没有完整的推进路径

_inspectAndContinue() 已处理 parent、business/proof、prepare/complete、child、retire，但未定义 successor、acknowledge、close 的恢复推进分支。successor 与 ACK 可进入“requires separate explicit resolution”兜底；close 还可能更早被已退役父 session 的 _current() 检查阻断。UI 的继续操作仍进入该方法，而 unfinished commit 会阻止工作区关闭。

因此存在“业务已提交、S2 也已持久化，但 ACK 或 capture-close 结果不明确，操作仍无法收尾”的条件路径。它是可恢复性缺口，不能称为已观测到的数据损坏。应补原身份的只读观察、必要终态证明和一次性消费，而不是对整段 finish() 自动重试。

已实现与缺失的恢复分支；ACK/close 顺序；unfinished commit 关闭门禁。

B5 · 16 个活跃槽可释放，256 个历史身份仍会累积

host 定义 MAX_SLOTS=16 与 MAX_JOURNALS=256。all_draft_metadata() 收集包含 inactive 的全部 journal；新身份在总数达到 256 时被拒绝。discard 只将 journal 写成 active=false、active_bytes=0，不会删除其身份。S1→S2 的新 child 也会消耗新的草稿身份。

256 是累计保留的不同草稿 journal 身份数量，不是 256 次按键，也不是 256 次自动保存。18 次 live-owner 退役证明局部活跃额度可释放，不能证明长期身份预算不会耗尽。所需维护策略必须同时保护原操作回执、父子谱系、capture 归档及 Unknown；单纯增大常量会推迟触顶，却不能完成生命周期设计。

容量常量；全部历史身份扫描；新身份拒绝条件；discard 保留身份。

SDK26、G04 的含义

SDK26 是 F01–F26 的完整能力目标，不是 26 个测试。G04 是文件/附件能力门禁。目录编解码、native broker 和受限三语言 guest 已有分阶段实现，不能重复旧结论“目录 guest 完全没有”。G04 剩余项包括真实 picker/anchor 来源、Workbench 产品链、blob 耐久与历史恢复、upload/watch/rename，以及有可靠条件原子后端才能承诺的 replace。

对于此次 Windows 稳定候选，先明确具体命名 profile、协议摘要、权限和平台矩阵，然后验证该范围内的真实 API、资源终态及旧原包兼容。完整未来网络/Cloud/富 UI 能力不应自动成为一个小范围预览的前置，也不能因此被省略后宣称整个 SDK 已冻结。

目录 guest 增量及后续门禁；命名 profile 冻结原则。

开发线与 main 的整合风险

GitHub 比较显示当前开发线相对 main@4de7fe2d 为 diverged，ahead 98、behind 20。它不是 main 的线性后继。冻结前应核对两边的协议生成物、公共 schema、host 调用和 Web 修复的等效实现；提交差集本身不能证明某项功能缺失，也不构成自动合并的依据。

固定两头的分支比较。本次审查未执行源码合并或 CI；此页面作为文档归档提交，不构成产品修复或验收。

建议的整体推进顺序

工作包主要修改边界完成标准
A · Windows 启动对象合同actual R primary token 的观测与类型专用访问合同；保持 creator、runner、setup 的原边界。明确实际拒绝机制；业务子进程启动并收到 SpawnReady；最小真实业务完成；成功/拒绝的原次收尾可核对。
B · 完整退役native、registry、SDK、factory、account/setup；区分正常完成、可证明干净拒绝、Unknown。只有原事实完整时消费清理证明并释放额度；连续超过 16 次干净拒绝；原 owner finish 先于实际 scheduler shutdown。
C · 编辑器恢复retirement preflight、successor/ACK/close 终态、新授权下的可编辑重启、历史身份维护。逐个 await 边界的丢回执与失败矩阵；源卡冲突、双活、附件删除/重选、容量/磁盘、切库等均有明确终态。
D · 候选资格与集成固定源码、schema、产物、原包与调用者身份；明确 Windows profile；核对 main 分叉。原47步与Nine、scope 内 SDK/G04、正式 UI 和物理输入分别有可追溯结果；旧失败和 Unknown 不被新结果覆盖。

建议把每个异步阶段的四件事独立表达：业务效果是否发生、结果是否交付、原资源是否终止、额度是否可以归还。当前代码已在多处保留这种区分；下一轮应补全阶段转换和跨层消费接口，避免在每个 catch 中各写一套猜测与补偿。

同样，Windows 的检查应覆盖“实际要使用的对象、实际调用者、实际掩码”；编辑器的恢复应覆盖“持久证据到新授权的转换”；长期稳定应覆盖“活跃资源与历史身份的不同预算”。这些是当前调用链共同暴露的结构缺口。

性能观察的边界

源码可见两个值得后续测量的点：Dart 控制通道的串行队列，以及草稿保存对全部历史 journal 的扫描/解码。前者可能产生排队等待，后者的工作量随历史身份增长。这里没有性能 profile 或实际延迟测量，不能将它们写成已确认的 CPU、数据库或 UI 性能瓶颈。当前已有明确证据的首要卡点仍是权限对象、失败终态与生命周期合同。
