# UI 设计思想与架构原则

日期：2026-09-09  
状态：现阶段设计取向，依据本次讨论整理；不代表项目已完成相应实现或性能验证。

## 1. 核心主张

以独立业务核心为基础，优先保证资源效率、响应稳定性和交互质量。UI 负责交互与呈现，通过明确的业务接口使用核心能力，并具备跨平台扩展和未来替换的空间。

**核心是长期资产，UI 是可复用、可演进、可替换的交互层。**

## 2. 技术选型偏好

现阶段的优先顺序为：

**优质原生跨平台框架 > Flutter > Web 技术栈。**

这是个人项目的选型前提，不是对所有框架、应用和负载的绝对性能排名。“原生编译”与“使用系统原生控件”也应分别判断：原生跨平台框架可能采用自绘，并不自动获得完整的系统控件体验。

| 方案 | 定位 | 主要考虑 |
| --- | --- | --- |
| 优质原生跨平台框架 | 优先选择 | 资源效率、响应稳定性、底层控制及平台适配质量 |
| Flutter | 可接受的跨平台方案 | UI 复用、视觉一致性、开发维护成本，以及与独立核心的连接能力 |
| Web 技术栈 | 默认避免 | 浏览器运行环境负担、依赖膨胀，以及功能优先时优化容易长期滞后 |

对 Web 技术栈的主要顾虑，是开发侧的便利可能转化为用户侧的启动等待、内存占用和操作延迟。多个应用各自携带浏览器运行环境时，这些成本还会累积。

该顾虑不等于“所有 Web 方案都附带 Chromium”或“JS 始终逐句解释执行”。Electron 与系统 WebView 的运行时部署方式不同；现代 JS 引擎也会使用 JIT 编译热点代码。需要评估的是应用的整体成本，而不是仅凭语言标签判断性能。

CSS 相关开销主要涉及样式计算、布局、绘制和合成，以及不合理更新导致的重复工作。原生 UI 同样存在布局和绘制成本，最终应以实际负载下的结果比较。

## 3. 核心与 UI 的职责边界

业务逻辑与 UI 完全分离，但 UI 保留完成交互所必需的本地逻辑。

| 独立业务核心 | UI 层 |
| --- | --- |
| 业务规则、业务校验和状态转换 | 输入采集、命令触发和结果展示 |
| 权威业务状态及任务生命周期 | 展示快照和临时交互状态 |
| 任务调度、耗时计算及业务 I/O | 焦点、导航、滚动、动画和视觉反馈 |
| 错误定义、取消语义和执行结果 | 错误呈现及用户操作引导 |

业务状态只有一个权威来源。UI 可以缓存展示数据，但不应形成另一套独立裁决业务结果的逻辑。输入格式提示可以在 UI 即时完成，业务约束仍由核心执行。

Flutter 方案下，业务处理放在 FFI 后的核心，Dart 侧主要承担交互与呈现。此处不限定核心实现语言。

## 4. 命令、消息与异步结果

通信采用以下闭环：

```text
UI 输入 → 业务命令 → 通信适配层 → 核心队列 → 业务执行
UI 更新 ← 状态／事件／结果 ← 通信适配层 ← 独立业务核心
```

设计约束：

1. **提交与执行分离。** 耗时任务的 FFI 入口尽快返回，以请求 ID 关联后续结果；实际处理交给核心执行环境。
2. **界面更新由前端调度。** 回调负责安全投递消息，不从任意核心工作线程直接操作 Flutter UI。
3. **明确任务生命周期。** 定义成功、失败、取消、超时及过期结果的处理规则；取消请求与取消完成应有明确区别。
4. **控制消息压力。** 队列容量和过载策略需要明确；进度等可替代消息允许合并，关键结果不能静默丢失。
5. **明确资源所有权。** 跨 FFI 的数据、缓冲区和回调句柄应规定释放责任，订阅能够解除，前端销毁后不再向其投递消息。

跨边界传递语义操作，例如“创建任务”“取消任务”和“任务进度变化”。鼠标悬停、每帧动画、进度条插值等视觉细节留在 UI，避免不必要的跨边界往返。

## 5. 为前端替换设计接口

接口围绕业务能力定义，不依赖 Widget、页面名称或 Flutter 专属对象。

基础能力应包括：

- 创建和控制业务任务。
- 查询完整业务状态。
- 订阅状态变化、执行结果和错误事件。
- 恢复订阅并重新同步状态。
- 查询核心能力和必要的协议版本信息。

不能仅依赖一次性回调推送增量。新前端接入、窗口重建或订阅中断后，应能够重新获取完整状态；状态快照与后续事件之间也需要约定一致性和顺序，避免遗漏更新。

长期维护的对象是业务协议及其语义。FFI 是本地进程内的承载方式，可替换的通信适配层使未来原生 UI、CLI 或多个客户端能够复用核心能力。

## 6. Flutter 与 Web 覆盖

Flutter 的价值包括共享组件、主题、布局和交互实现，并为部分浏览器场景提供同一套 UI。对于应用型界面，这可以减少额外维护 HTML/CSS 前端的需要。

视觉目标是**高度可控的一致性**。字体、缩放、浏览器环境及平台视图仍需验证，不将所有环境逐像素一致作为默认保证；视觉一致也不意味着平台能力或性能完全一致。

浏览器端不能直接沿用本地 `dart:ffi` 调用动态库，需要独立适配：

| 运行场景 | 核心连接方式 | 需要处理的边界 |
| --- | --- | --- |
| 桌面／移动端 | FFI 连接本地核心 | 线程、内存所有权、回调和应用生命周期 |
| 浏览器端，本地计算 | 将可移植核心编译为 Wasm，并提供互操作适配 | 核心依赖与浏览器能力的兼容性 |
| 浏览器端，服务提供能力 | 通过网络协议连接核心服务 | 身份验证、连接中断、延迟与状态恢复 |

以上是可选架构路径，不表示核心可以未经改造直接移植。不同平台复用业务命令和事件语义，由适配层处理传输差异和能力限制。

## 7. 评估与演进原则

选型和实现应关注冷启动、空闲资源占用、交互延迟、长任务期间的响应，以及长时间运行后的稳定性。具体预算应结合产品目标制定，不预设缺乏测量依据的数值。

FFI 拆分改善的是业务边界、执行组织和可替换性，不会消除 Flutter 自身的运行时、布局、渲染或通信成本。原生框架的优势同样需要实现质量和实际测试支撑。

当前可以采用 Flutter 交付，同时保持核心独立；未来根据需求替换原生前端，或增加浏览器入口。演进时优先保留核心能力与业务协议，调整 UI 和平台通信适配。
