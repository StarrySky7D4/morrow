# 编辑器持久保存与恢复：剩余接线

本计划基于 2026-09-23 的实际代码核验。已有独立正文草稿、可释放附件归属、导入与放弃决定 journal、原生扫描和恢复入口；不把这些接口等同于正式编辑器已经启用自动保存。完整目标继续包含正文/附件/来源的跨重启恢复。

## 会话归属与附件来源

让工作台会话持有 EditorDraftSession，视图通过 EditorDraftBinding 连接五个 TextEditingController 和 category/stage。界面隐藏、路由关闭与内容库更换是不同事件。原始文本、选区、方向、输入法组合区均进入快照，不能用业务正文相同判断当前视图没变。

附件选择需要独立的 provenance 表：source、predecessor、staged、previousDraft，以及原导入操作、逻辑附件 ID、别名。不能从 IdeaAttachment.pluginId 或文件路径猜来源。新文件先固定操作做 durable Begin/Complete，Ready 确认后才交给草稿保存；未解决附件使整个快照显示未持久保存，不能静默省略。恢复预览应导出已核验的 pin，不重开原路径，不把未知结果当失败重选。

## S1 提交与 S2 后继

一个 draftId 的 sourceKind/sourceRevision/predecessorOperation/digest 不可改变。S1 在途时 S2 继续留在当前会话；S1 确认后为后继草稿分配新的身份，从已核验的精确操作/摘要建立前驱。不能将正式提交后的 canonical 附件当作旧源修订的附件，也不能覆写旧 journal 的不可变基线。

新 S2 的完整快照及附件归属确认持久后，才可退休旧槽；如果中途退出或回复丢失，重启能够区分旧待决提案、已确认 S1 与仍未提交 S2。旧回执不能关闭具有新原始编辑状态的窗口。仅选区/方向变化遗漏已修复，但这不完成持久来源交接。

## 正式关闭与恢复

当前 NewIdeaDialog.dispose 会关闭捕获 scope 并清理 created 本地附件。启用 autosave 前必须将退出变成显式状态流程：先固定当前快照、确认可恢复附件；等待/检查/保留未确认原操作，而不是由 dispose 猜测成功或自动重发。释放视图不得释放唯一恢复来源。

恢复列表先只读展示原来源和冲突；明确选择恢复后才建立新编辑会话。将原始值应用到五个控制器时暂停旧 generation 监听，避免恢复本身制造新的 S2；绑定后立即读取完整 metadata。当前来源修订、权限和插件可用性必须重新核验。

富剪贴板捕获包含观察、转换票据和来源链。无法恢复这些证据时必须明确保留未完成状态，不能把它降格成无来源文本而宣称恢复完整，也不能自动再执行插件。

## 必要验收

- 未输入标题的新卡片：空白草稿持久化不产生正式内容。
- 正文、选区、输入法及附件混合编辑：进程退出后从宿主恢复，不读取旧本地路径。
- S1 已提交但回执丢失、S2 后继保存中断：不重复正式业务、不丢后继、不重写旧来源。
- 关闭、切库、语言/字体切换：迟到回复不更新新工作区；当前唯一草稿有明确所有者。
- 本地附件导入失败、磁盘满、历史上限、清理失败：未确认状态可见，资源继续计费，旧决定不可复活。
- 原始富捕获/转换身份失效：不偷偷重跑或丢证据。
- 活动草稿和累计身份容量：提供查看、导出、显式退休及长期维护；有限上限不能作为无限期 autosave 已完成的依据。

正式迁移 UI、语言/字体待决提案、完整错误协议与诊断、远端 Unknown、SDK 与其他平台资格仍按总看板推进，未被本计划缩小或替代。

## 宿主后继交接的实施约束（宿主与私有协议已验证，正式 UI 待接线）

当前 previousDraft 只指向同一 draftId 的上一代。仅在 Dart 中另建会话、复制 assetId 或先 discard 旧槽，都不足以支持跨重启后继。宿主交接必须同时遵守以下项，不能只开放跨草稿读附件：

1. 子草稿固定父 cardId/draftId、父代次、父保存操作与精确摘要，以及正式 S1 的操作和证据摘要。宿主确认 S1 实际已提交；仅有恢复提案或 guest 回执不构成提交证明。新卡第一次正式提交后，子草稿应切换到已有卡片来源，并绑定提交后的真实修订。
2. 子槽第一次写入时核验父槽仍活动且代次相同，复制所选父 pin 的受控归属，与完整子快照在一个子槽事务中落盘。新增显式父草稿附件来源，不把它混入同槽 previousDraft。正文/附件缺一项则整次失败，父槽保持可恢复。
3. 同一父代次只允许一个后继身份。现有单 owner 内，在业务串行边界检索持久父子关系并提交；不能仅靠内存 Map 去重。已退休子槽也保留该关系，不能以隐藏历史或删除列表项重新获得建子资格。精确旧操作重试先返回历史，不生成第二个子槽。
4. 子槽确认持久后才条件性退休父槽。两个私有 CardRecord 不假装支持跨记录原子事务：允许“父子均活动”的中间状态，但重启扫描必须据持久关系识别后继。父槽新写入在已建立后继后拒绝，旧历史回执仍可核对。父退休回执丢失时只核对原操作。
5. 容量不足、子写失败、提交结果未知时保留父槽和唯一 S2，不先删除旧槽腾空间。当前 16 活动槽、256 累计身份与修订上限仍是长期维护任务，不能作为无限期自动保存的设计终点。
6. 同槽保存也有资源代次边界：S1 删除上一代附件后，S2 若重新选回该附件，必须在旧 pin 释放前取得独立持久归属，或明确阻止未持久的重新选择。客户端 catalog 不得继续声明旧 pin 可用；仅保留未被消费且仍受宿主核验的 Ready 导入。

对应故障验收需包含：S1 提交但回执丢失、子槽已提交但回执丢失、父退休失败、双活动重启、竞争后继、旧父迟到保存、父/子基线变化、来源附件消失及活动槽/历史容量耗尽。验收要验证真实宿主字节与操作记录，不只检查客户端对象相等。

## 私有协议已接通；下一切片：持久交接提案与编辑器会话

上述宿主约束已由[宿主报告](../reports/editor-draft-handoff-host-2026-09-23.md)验证。[私有协议与客户端](../reports/editor-draft-handoff-wire-2026-09-23.md)现已提供 ParentLink、Retirement、parent 附件来源、分页关系及 handoff/条件退休请求，沿用整段串行传输、限额、精确 u64 和丢首回执缓冲清理。宿主回传精确 Protobuf 请求摘要，客户端不能用 Capnp 摘要代替。三代关系允许中间草稿同时继承上一代并退休给下一代。客户端必须固定完整原 child 请求和父/S1 证明；不能用随机新 child 身份重试 Unknown。

交接提案本身的跨应用重启发现/核对仍需补齐。S1恢复证据的确认清理要安排在子草稿交接可恢复之后，不能先丢掉关联再仅凭当前卡修订猜原操作。界面在所有原始输入及附件元数据成功捕获后，保存父最新代、建立子、明确核对原交接、条件退休父，最后才释放旧会话。测试应新增真实客户端进程退出、扣留首回执、分段损坏、切库与固定操作重试；现有宿主对象重开只证明数据库持久边界。
