对来源方案的五处收紧：

1. “有限 IO”只代表首批有界实现。完整目标仍含调用第三方 API 和自身发布 API；不能将已要求的服务端能力整体推到长期研究。继续保留 [NET-1–NET-8](PLUGIN_NETWORK_API.md) 与 [NODE-1–NODE-7](PLUGIN_API_NODE.md)。
2. 外部系统不一定提供去重或状态查询。Unknown 的交付标准是能保留并解释不确定结果、按提供者能力核对；不能保证所有第三方写入都可自动确认，更不能承诺跨网络事务的 exactly-once。
3. Android 独立 Service 承载随 APK 编译的 Rust/Wasm 执行引擎，与开放第三方原生库插件是两件事。前者属于早期平台任务，不能等待 ROAD-11 的原生插件收益论证。
4. “以执行域为强边界”必须落实到平台真实隔离能力。普通同 UID 进程只提供部分故障隔离；SDK、线程和函数表不能阻止恶意原生代码旁路访问。
5. 技术路线末尾“不预设下一稳定版本号”修正为：稳定目标已确定为 `0.2.0`；不预设最终 test 序号、发布日期或按测试次数宣告稳定。test.1 兼容分界和后续第一方 AGPL-3.0-only 规则沿用。

## 2. 采用的设计及未锁定的选择

### 身份、语言和内容

新增业务使用稳定类型／页面／阶段／错误标识，业务扩展定义自己的阶段语义，核心不枚举所有业务。旧中文记录通过版本化读取和迁移适配解释；未知值保留，已签历史和原始附件不改写。迁移在可恢复副本上产生新记录和来源关系。

采用 `LiteralText` 与类型化 `MessageRef` 的设计方向，具体名称及 wire 版本待 ROAD-02 固定。宿主权限／恢复消息使用受保护命名空间；插件不能提供或替换宿主授权提示。用户正文不自动翻译。任务固定自己的语言与格式上下文，界面切换不改变运行中任务的输出语言。

先交付简体中文、英文与伪本地化压力场景。Flutter 复用 Localizations、delegate 与 supportedLocales，自有语言资源批量准备并只读缓存；布局过程不逐词跨 FFI。正式语言包仍使用 Protobuf＋LZ4，开发源格式和 Flutter 框架资源另按构建输入管理，避免两份应用自有权威词库。[Flutter 官方机制](https://docs.flutter.dev/ui/internationalization)

现成消息引擎、CLDR 数据裁剪、字体和 RTL 支持由样例比较后决定，不同时引入多套消息执行器。语言包作为有配额、版本和摘要的数据资源管理，不因安装语言包启动执行线程。首期不增加 TS／JS 或动态 Dart 插件要求。

### 协议与 SDK

旧同步接口及 guest-v1-rc1 原包保留，新协议由显式声明、能力发现、精确摘要和版本路由接入。Cap’n Proto 的兼容追加规则不等于本仓库摘要门禁自动接受新文件；注释修改也不得覆盖冻结原件。[Cap’n Proto 版本规则](https://capnproto.org/language.html)

C、C++、Rust 共用业务语义与负面向量。原生 ABI 只承载受控缓冲／句柄及明确的 create/invoke/stop/destroy 生命周期；Rust 对象和 C++ STL 不跨 ABI。现有回调适配不升级宣传为原生插件装载协议。UI 仍由 Flutter 绘制，资源和媒体走受控平台通道。

签名验证针对保存的原始字节，业务身份与序列化摘要分开；不能解码再编码作为历史验签或去重依据。[Protobuf 非规范化序列化说明](https://protobuf.dev/programming-guides/serialization-not-canonical/)

### 执行域与调度

可信宿主保留资料库、授权、审计和平台代办。执行引擎处理获准输入和结果提案。默认延续受限 Wasm；第三方原生扩展按独立平台配置准入，不进入 Flutter／核心进程。

按可重入短调用、实例串行、有界并行、线程亲和和库自带线程池分别调度；全局许可约束嵌套并行，根任务期限／取消／预算沿依赖链传递。跨域调用不占满同一线程池等待子任务，不持数据库锁等待插件或 IO。共驻前明确共同故障与信任范围，低内存不能静默合并必须隔离的域。

ROAD-11 首期优先排空旧域、启动新域并重绑定，不做任意热卸载。新 FFI／平台模块的安全边界另作具体实现审查；本次方案没有扩大此前仅针对 Windows shared_memory.rs 的受控 unsafe 批准范围。

### 完整双向 IO 与副作用

ROAD-07 同时承接正式出站请求与入站路由最小闭环：资源声明／Registry 批准 → Manager／Pool 当前实例 → 宿主 broker → 受信任传输 → 类型化结果／证据。复用 network_node，禁止以另一个授权文件或固定 CLI token 代替主应用授权权威。

出站 origin／方法、文件读写、监听、路由发布、凭据使用与远端主体分别授权；入站主体、路由范围和插件当前授权取交集。外部调用者不能选择任意包、URL、宿主路径或提升委托权限。文件选择返回资源引用，创建／替换／删除也纳入文件范围与撤权复核，不能仅交付读取。

第一个可能产生外部效果的调用就包含稳定 operationId、命令匹配、持久意图、期限、取消、结果查询和审计接纳。故障后区分未开始、已确认、失败和 Unknown；提供者支持时使用幂等键／状态查询，缺失时保留人工核对入口。不能因 GET、超时、取消或连接断开便推断没有副作用。

后续按原 NET/NODE 任务补齐 OAuth／多账号、REST／GraphQL、上传下载、分页限流、流／SSE／WebSocket、webhook、持久服务、TLS 部署与证书轮换。gRPC／签名／企业连接等维持独立 profile；逐项验证且明确未支持范围。自有外部业务使用 Protobuf＋LZ4，第三方既定格式在边缘适配；重放使用录制响应并禁用真实外发。

### 容量、证据和产品

ROAD-06 复用 [归档退休合同](PLUGIN_ARCHIVE_RETENTION.md)，补已发布材料的合法清理、满盘下收尾预算、永久操作身份及签名关联。材料缺失、合法退休与仍可完整重放分开表达；映射／备份仍持有引用时不宣称物理擦除。

ROAD-08 要保存实际 A/B 和依赖产物、授权与固定输入、宿主投影、输出及提交／封存关系。删除原安装目录后仍能独立核验，隔离重放不得写生产库或产生真实网络效果。已有纯转换／查询报告不能替代这项整链验收。

产品线以“收集→整理→处理→找回”为样例，推进公开正文／附件／草稿接口、必需依赖管理、视图配置和虚拟化瀑布流。卡片进入视口不自动启动重型插件；摘要、缓存预览和完整编辑分层，主题与媒体能力复用现有实现。

IO-A／B 可以独立合并，但不能将元数据批准宣传为可用网络能力；IO-C 必须先于 IO-D 的任何外部效果开放。IO-D 内部可分多次交付，不能用一次 GET、仅客户端或文件读取替代整项完成。具体字段、绑定和迁移约束见 [IO 设计](PLUGIN_IO_DESIGN.md)。

并行任务优先选接口明确的负面测试、ROAD-02 消息设计、ROAD-12／AND-01 探针和 ROAD-01 主应用回执接入。类别／阶段正文迁移仍需独立设计，不在 UI 标签调整中顺带执行。

负责人／主代理维护唯一契约与迁移整合入口；子代理可独立完成平台探针、固定接口 UI、负面测试和文档审查，交接需包含基线、允许目录、接口版本、证据和未测范围。构建目录隔离，最终候选产物顺序构建并重算摘要。
