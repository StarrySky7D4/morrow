# 网络作业的原存储所有权

运行时支持把完整受保护存储容器交给 IO 执行线程。Windows 工作台 `Storage` 的适配已通过实际审计会话、受管 Wasm 与本机 HTTP 验证；Workbench Rust 应用入口已使用显式所有权状态，CLI／Flutter 的任务启动与面板仍待接线。应用保持 `0.1.9-test.52+56`。

## 完整容器与独立实例

`IoWorker<O = HostRuntime>` 使用受信任宿主的 `HostOwner`。该容器提供原运行时的借用、写入前维护和退出封存，不拆分或重新打开数据库。Windows 的 `Storage` 随原审计 Session、签名身份、数据库锁、身份租约及活动库 Registry 一起移动到工作线程。

IO 实例由原 Manager 在同一 HostRuntime 上明确准入。现有 Pool 保留其根实例和共享依赖，不将 `Pool::root()` 的借用转换为独立所有者，也不复制实例。Manager 留在调用侧，原批准变化仍能立即撤销正在执行的 IO。

`spawn_managed_owned` 核对原 Manager、实例、IoBinding、声明预算和原运行时身份；执行与 Store 修改继续借用同一个运行时。`HostOwner` 是宿主实现接口，不是给 guest 的任意内存或权限入口；不得通过维护回调替换运行时、恢复旧授权或重入执行器。

## 完成、失败与取回

- `try_reclaim()` 仅在实际线程结束后归还 `WorkerExit<O>`，包括完整原容器、执行结果、断连结果与维护结果。
- 创建校验或线程启动失败通过 `Box<SpawnFailure<O>>` 归还原容器及原受管实例，供调用方明确清理；不自动打开另一份内容库重试。
- 执行或准备维护失败先撤权；执行 panic 也尝试断开原连接并封存。断连未确认时保留原实例，调用方可以在修复容器后准确清理，不凭空创建连接代替。若发现运行时已被替换，跳过结束维护并明确报告，防止维护另一份 Store。
- 退出封存失败与执行结果分开保存。已提交或 Observed 的外部效果不能因维护失败变回“未执行”，也不能自动重发；取回原容器后可明确重试封存。
- `Drop` 只请求停止并立即返回。同步路由尚未返回时，容器及锁仍在线程内；停止请求不能当作线程已结束。迟到结果沿用原取消与交付检查。
- 默认 `IoWorker<HostRuntime>` 保留原 `spawn`、`spawn_managed` 和 `try_finish` 调用形式。需要异常后回收受保护状态的宿主使用新的完整容器接口。

## 维护边界

`Storage::prepare_io` 复用既有 `prepare_write`，在需要时先完成有界审计封存；失败会阻止本次外部操作。`finish_io` 复用 `flush_pending` 并保留维护警告。没有新建签名器、替代 Store 或绕过租约。只读恢复查询不触发写入前维护；容器退出时的正常生命周期封存单独处理。

这层只建立安全可恢复的所有权交接。业务操作是否允许、请求是否已有副作用、Ready 是否可交付，仍由原 Manager、Broker、持久意图和资源守卫决定。

## 主应用后续接线

[主应用任务状态](PLUGIN_APP_IO_TASKS.md)已区分存储在调用线程、在线程执行、停止待退出、已取回及待修复。Workbench Rust 入口可在原实例上启动、查询、读取、取消和回收任务；既有私有协议会在依赖存储的副作用前返回 Busy。存储不在当前线程时不重新开库。下一步接具体端点批准和 CLI／Flutter 的短响应任务消息，并处理 EOF／关闭等待退出；原 Manager 继续保留在调用侧。

任务配置还需接入具体端点批准、凭据引用和真实独立插件调用；主应用完整路径验证后，再扩展 API 节点配置、文件系统与三语言 IO SDK。此项不意味着 SDK 整体稳定或全平台运行完成。
