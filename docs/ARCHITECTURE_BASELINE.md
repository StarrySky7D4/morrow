# Morrow 统一架构总结

**Morrow 的目标是一个全平台、本地优先、卡片化和插件化的内容工作台，以瀑布流作为主要入口；MorrowCloud 是独立开发、通过通用插件机制接入的可选服务，不是核心依赖。**

目前应当固定的是**内容归属、协议分工、权限边界、操作提交与审计规则**；运行时、进程布局和具体性能参数，继续通过原型验证决定。

以下是本轮形成的设计基线，**不代表这些能力已经全部实现**。

---

## 一、产品与内容模型

### 卡片是内容，插件是能力，瀑布流是视图

**卡片**具有稳定 ID、内容类型、格式版本、修订、正文、附件和关联关系。它可以同时出现在多个工作区，不需要复制内容或改变身份。

**插件**提供类型编辑、格式转换、计算、预览、业务操作与服务连接。插件可以被替换、禁用和卸载，但不能因此删除用户内容。

**瀑布流**负责浏览、排列、选择、拖动和展开。卡片尺寸、折叠状态、排序和所在视图，与卡片本体分开保存。

需要坚持：

> **插件消失后，用户仍能读取基础信息、查看已有预览、保留未知字段和导出原始附件。**

一张卡出现在视口中，不应必然启动插件；应优先使用摘要与缓存预览，完整编辑、计算和重型解析按需运行。

---

## 二、推荐技术路线：Flutter＋可移植 Rust 核心＋可替换插件执行后端

这仍是推荐主路线，**不是已经锁定所有运行时与库的最终选型**。

| 层次 | 主要职责 |
|---|---|
| **Flutter／Dart** | 导航、瀑布流、卡片外壳、输入、选区、拖动、主题、玻璃效果、插件界面绘制 |
| **可移植 Rust 核心** | 内容事务、协议校验、权限、依赖、任务、持久化、审计、证据和重放协调 |
| **平台适配层** | 文件、凭据、存储后端、共享内存、进程／Worker、通知、平台媒体能力 |
| **插件执行后端** | 承载可独立安装的插件逻辑，执行授权、限额和生命周期规则 |
| **独立验证工具** | 复用核心代码，完成审计验证、数据迁移检查与隔离重放，不依赖 Flutter 界面 |

Wasm 是外部插件执行格式的主要候选；Wasmtime、解释执行或其他后端仍需按平台验证，不能把某个运行时写成全平台的唯一前提。

Flutter 继续维护界面状态，但**正式内容只有一个权威来源**。不得在 Dart 和 Rust 中分别维护两套独立保存、迁移与修改逻辑。

同进程的 Flutter 与 Rust 核心属于同一可信范围，不宣称彼此具有强安全隔离。是否进一步拆出核心进程，由故障隔离需求和测试结果决定。

---

## 三、全平台是架构约束，不是后续移植任务

目标覆盖 **Windows、macOS、Linux、Android、iOS／iPadOS、Web**，并为其他平台保留接入边界。

可以先在某个平台验证完整流程，但公共协议不得绑定 Windows 路径、原生句柄、特定剪贴板格式或某一种进程模型。

统一的是：

**内容模型、业务语义、权限范围、操作结果、协议版本与审计关联。**

平台分别实现：

**实际存储、共享内存、执行隔离、强制停止、密钥保护和分发机制。**

能力不足时要明确报告、拒绝或经确认降级，不能偷偷扩大权限，也不能把“能够读取卡片”宣传为“完整支持该插件”。

原生 mmap 与浏览器共享缓冲区可以承载同一份协议，但不假装具有相同的内存保护和执行能力。

---

## 四、协议分工：运行期 Cap’n Proto，持久化与外部交换 Protobuf＋LZ4

**“内外”按数据用途划分，不按是否在本机、是否跨语言或跨进程划分。**

| 路径 | 协议与机制 |
|---|---|
| 宿主 ↔ 插件、插件 ↔ 插件 | **预编译 Cap’n Proto＋受控 mmap／对应平台传输后端** |
| Flutter／Dart ↔ Rust、宿主 ↔ Wasm | **可使用 Cap’n Proto 辅助传递结构化数据**，由 FFI、线性内存适配或消息机制承载 |
| 进程内普通函数与局部 UI 状态 | 类型化对象直接调用，不强行序列化 |
| 卡片、配置、插件状态、依赖锁定、持久授权配置 | **Protobuf＋LZ4** |
| 审计、诊断日志、检查点、缓存、任务恢复状态 | **Protobuf＋LZ4** |
| 快照、重放证据、备份和导出 | **Protobuf＋LZ4** |
| 自有网络与外部系统接口 | **Protobuf＋LZ4** |

### 固定契约，但允许版本化扩展

所有 Schema 纳入版本控制并预编译。运行前确定接口、版本和摘要，运行时仍进行边界、结构和资源校验。

宿主协议负责身份、权限、调用、内容提交和审计；业务插件可以具有独立的版本化契约。**新增专业业务不应必然要求修改核心，但业务载荷也不能夹带未经授权的特权操作。**

内外统一业务含义，不要求 `.capnp` 与 `.proto` 机械同构。网络请求、长期存储和内部调用可以使用不同消息类型，由明确的类型化适配层转换。

### JSON 不进入核心链路

JSON 不作为自有通信、配置、插件状态、日志或缓存的正式格式，也不作为 Cap’n Proto 与 Protobuf 之间的中间表示。

例外限制在用户原始内容、旧数据迁移和不可控第三方接口。可读配置、调试输出可以存在，但不能与正式二进制记录同时成为两个权威来源。

原始图片、音视频、文档和建模文件保留原字节；Protobuf 描述和引用这些载荷，不进行无关格式转换。存储引擎自身的页、索引和事务文件，由引擎管理，不要求重新包装成 Protobuf。

---

## 五、共享内存规则：发布后不可变，授权与实际可访问范围一致

Cap’n Proto＋mmap 的目标是**减少接口复杂度与重复搬运**，不是无条件追求全链路零复制。

共享数据采用：

**分配 → 写入 → 固定与校验 → 发布只读对象 → 租借使用 → 退休 → 确认释放后回收。**

其中最重要的约束是：

**权限检查、实际执行、审计摘要和重放材料，必须针对同一份固定内容。**

接收方只读不代表发送方不能继续修改。无法证明发布后不可变时，应在可信边界进行必要复制，再将固定对象交付后续消费者。

共享对象必须绑定身份、代次、长度、段信息、内容摘要和租约。过期消息与迟到结果不得访问新对象。

**旧映射尚未释放，就不能把同一片页面重新分配给另一个权限范围。** 代次检查只能拒绝旧请求，不能让仍存在的映射自动失去读取能力。

FFI 指针、mmap 偏移、Wasm 内存偏移和权限句柄都是运行期对象，不能持久化后重新当作有效能力。

---

## 六、插件底座与现有组件归属

原则是：**大规模模块化，选择性插件化；不把每个控件、公共机制和逻辑模块都拆成可安装插件或独立进程。**

| 归属 | 内容 |
|---|---|
| **内容核心** | 卡片、关系、修订、事务、附件管理、基础检索、恢复与导出 |
| **运行核心** | 权限、插件管理、依赖绑定、任务、资源回收、受控通信 |
| **审计核心** | 事件生成、持久化关联、封存、验证、证据与重放协调 |
| **UI／平台基础设施** | 窗口、主题、玻璃材质、瀑布流、焦点、公共交互、媒体会话 |
| **业务扩展** | 项目、实验、富内容转换、专业格式处理、音乐功能 |
| **资源扩展** | 主题参数、模板、纹理和提示语，不必执行代码 |
| **独立服务插件** | MorrowCloud，以及未来其他服务提供者 |

音乐的播放列表、歌词和界面适合插件化；通用解码、附件播放和音频资源协调留在公共服务中。

项目与实验扩展注册类型、字段、视图和操作，核心不再硬编码具体业务页面与中文阶段字符串。

第一方随包模块可以作为迁移阶段的组织形式，但应明确：**随包编译、可禁用，不等于动态插件，更不等于安全沙箱。** 正式插件无论官方或第三方，都不能获得绕过内容 API 和审计的私有入口。

## 七、权限、运行与依赖管理

### 权限按能力、对象、范围和期限授予

插件清单只提出申请。实际权限由宿主结合用户授权、工作区策略、平台能力和本次上下文决定。

内容查询、搜索结果、变更日志、附件名、缩略图和网络访问，都遵守同一授权范围。插件创建的卡片也不因此永久归该插件控制。

宿主绑定调用者身份，不相信请求中自报的插件 ID。每次激活生成新实例代次，撤销后的句柄与旧实例结果不得产生新的有效操作。

### 生命周期分层管理

插件包、用户启用状态、运行实例、任务和卡片视图分别管理。

正常流程为：

**安装校验 → 静态注册 → 依赖解析 → 受限准备 → 发布就绪 → 执行 → 停止接单 → 限时排空 → 撤权与回收。**

安全停止先撤权，再取消与终止，不等待插件自觉清理。用户内容不能依赖退出回调才首次保存。

插件故障按任务、服务和实例范围隔离；网络失败不默认重启整个插件。自动恢复有预算，连续异常进入可解释的隔离状态。

### 依赖不自动传递权限

依赖优先指向版本化接口，由宿主锁定具体提供者、包摘要和服务代次。

必需依赖与可选依赖分开，推荐安装集合不等于运行依赖。强启动依赖拒绝环路；运行期还要处理等待环、事件循环、期限和取消传播。

提供者更新或崩溃后重新绑定，旧服务句柄不能继续使用。停止消费者只释放自己的租约，不误停其他插件仍在使用的提供者。

## 八、审计与重放：固定证据，准确表达保证

### 三类记录分开

**审计记录**由宿主产生，记录授权、数据交付、调用、提交与故障等事实。

**诊断日志**允许插件报告解释与进度，但不作为“操作成功”的权威依据。

**重放证据**保存历史程序、依赖、输入、状态和必要的宿主响应，通过操作身份与审计关联。

正式审计原件使用 **Protobuf 固定字节＋完整性保护＋LZ4 分段持久化**。签名验证基于原始字节，不能解析后重新序列化再验证。

需要保留内部 Cap’n Proto 原始消息时，将它作为 Protobuf 证据记录的二进制载荷保存；其中旧权限引用只用于解释历史，不能直接恢复为有效授权。

### 不可篡改保证必须分层

应当保证：

**插件不能修改账本；已封存历史能够验证；具有独立较新检查点时，能够检测相应范围内的历史回滚。**

不承诺已经控制全部宿主、密钥和存储副本的攻击者仍无法伪造历史。签名证明记录来源与完整性，不证明插件结论正确。

MorrowCloud 可以传输归档或检查点，但不能成为唯一见证，也不能获得日志签名权。

### 内容提交与审计关联必须可恢复

本地内容修改与对应事务事件／待封存事件原子关联。封存按稳定事件 ID 幂等完成。

明确区分：

**未提交、已本地提交、已封存、已独立见证、结果待核对。**

超时不等于未执行，崩溃不自动回滚已经成功的步骤。审计无法承接必要事件时，不继续执行需要该保证的新操作。

### 重放分级，不承诺所有任务逐位重算

首期目标应为：

**全部受控业务操作可追溯；内容修改可重建；纯转换与计算任务优先支持确定性重放；外部效果采用录制式重放。**

重放默认在隔离副本中执行，不真实上传、不修改生产资料库、不使用生产凭据。

摘要只能验证证据，不能代替证据。材料过期、删除或环境缺失后，必须改变重放状态，不能继续宣称完整可重现。

## 九、MorrowCloud 的最终边界

**MorrowCloud 是普通规则下的独立官方插件，而不是特殊核心模块。**

它通过通用接口读取获授权内容、消费变更、访问附件、提交远端修改，并管理自己的账户、服务协议、映射与检查点。

核心不包含品牌专属账号页、服务器地址、同步业务或收费状态；插件安装和本地使用也不依赖 MorrowCloud 登录。

移除 MorrowCloud 后，本地工作台仍完整可用。已有本地内容保留；仅存云端、尚未下载的附件需在停用或卸载前明确提示。

## 十、下一阶段：冻结边界，验证实现

**现在不再继续扩大首版架构范围，而是完成一条贯通流程。**

建议先验证：

> 插件 A 获得授权输入，经 Cap’n Proto＋受控共享对象交给插件 B；B 生成结果；核心提交卡片并形成审计；独立工具能够验证证据，并在隔离环境中重放该任务。

实施顺序为：

**内容与协议契约 → 可靠持久化及提交 → 共享对象与权限原型 → 审计封存和故障恢复 → 受限重放 → 真实业务插件 → 各平台一致性验收。**

具体数据库、Wasm 运行时、桥接库、进程数量、内存限额、超时参数和证明结构，保留为验证项。性能测试覆盖整条链的复制、校验、压缩、持久化、重绘与回收，而不是只比较编码速度。

---

## 最终基线

> **全平台 Flutter 界面，可移植 Rust 核心，平台化执行与系统适配；卡片承载内容，插件提供能力，瀑布流组织呈现。**
>
> **运行期以 Cap’n Proto 为统一契约，原生 IPC 以 mmap 为主要后端；全部自有持久化与外部交换采用 Protobuf＋LZ4，尽量避免 JSON。**
>
> **权限、内容提交、审计与资源回收由宿主统一控制；MorrowCloud 独立接入，不形成核心依赖。**

**最重要的不变量是：执行的内容就是检查过的内容，记录的结果就是实际提交的结果，重放使用的材料就是当时固定的材料；插件可以失效，用户内容与已形成的证据不能随之失去。**

## 补充：第三方 SDK 与界面接入（2026-09-11）

首期提供 C、C++、Rust SDK，共用运行期 Cap’n Proto 与宿主能力模型；暂不考虑 TS／JS 插件。插件通过声明式 UI 描述和动作协议接入，Flutter 宿主统一处理控件、主题、输入、窄屏及无障碍。持久草稿与内容仍由 Rust 核心提交；第三方无需提供 Dart Widget。

Dart 保留为宿主和随包组件语言；动态 Dart guest 支持仅作后续研究，不是 0.2.0 前置要求。SDK 不能代替执行隔离，也不能暴露授予权限、选择其他实例或直接打开 Store 的入口。具体设计、当前原型边界与验收任务见 [插件 SDK 与 UI](PLUGIN_SDK_AND_UI.md)。
