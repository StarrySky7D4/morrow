# 已发布读取归档的保留与清理设计

状态：test.47 的下一阶段设计，**尚未实现已发布归档清理**。本文件不是现有 API、已完成迁移或通过验收的声明。本轮正在加入全库 8192 档／64 GiB 逻辑预算及数据库格式 14 的派生用量账本；该变更限制增长，不删除 published 原件。当前默认查询、捕获状态和游标合同见 [分片归档](PLUGIN_READ_ARCHIVE.md)，真实生产回放资格见 [query_capture/tests.rs](../workbench_host/src/query_capture/tests.rs)。

## 当前必须保留的事实

原 `ReadObservation` 保存请求／响应原件及 `archive_sha256`，其完整容器进入永久操作索引、事件序列、outbox 和后续 Ed25519 封存。根摘要来自原 Manifest PB；有序 Part 的原 PB、容器、前驱及摘要共同构成完整归档。已签原件不可重编码、改根、改结果或从原事件中删掉引用。

`read_captures` 的 Ready 当前要求 Manifest、原读取观察和根链接同时存在，且 capture_binding 与原 Plan、context、owner、状态修订相符。Failed／Cancelled／Interrupted 保留操作身份，清理的是未发布暂存。当前 `abort_read_archive` 拒绝 published；不能借删除状态、清空 root 或将 published 改回 pending 绕过它。

现有 `lookup_read`、库完整性检查、签名备份和游标准入要求完整分片。直接执行 DELETE 会造成损坏；单独新增一张 tombstone 表也不足以让现有验证器接受缺片。下一阶段必须同时更新格式门禁、关联校验、读取接口、宿主交付和备份验证，再开放清理入口。

## 选择一个有限的首期清理范围

首期仅允许把一个已发布归档的**全部 Part 材料**主动退休，不提供任意删片、只删包、只留前 N 次调用或按分片年龄清理。清理命令由可信宿主显式发起；后台期限策略必须先形成可检查的候选清单，再逐档执行相同事务。期限和材料状态不是插件权限，不能沿用 DeleteContent 当作清理审计原件的授权。

下列原件继续永久保留：原读取观察及其请求／响应、原 Manifest PB 和容器、原操作索引和事件序列、全部已有签名段、tracked capture 的原状态／意图绑定，以及新清理操作的原件、链接和墓碑。既有未 tracked 的 published 归档沿用原空 capture_binding，不为清理补造 State。首期不触及 Card、附件、内容操作 TaskEvidence 或其共享块。这意味着清理可能仍保留敏感请求和结果；它不是个人数据完全擦除或安全擦盘。

**永久保留的是操作 ID 的不可复用性，不是可无限新增操作的承诺。** 原查询 ID 在清理前后都已占用；清理操作也有独立的全局操作 ID。即使原件迁移到未来的紧凑身份记录，必须在同一事务中把原 ID 转为永久保留记录，且所有 create/edit/aux/read/archive/capture 入口共同拒绝重用。首期不压缩或删除 State，因此不会通过清理解除现有 4096 个 capture 状态上限。

## 独立表示历史完成与材料可用性

保留 `Phase::Ready` 表达“当时计算及结果已原子提交”，另增版本化材料状态：

| 材料状态 | 可验证与可交付的内容 |
|---|---|
| Complete | 原观察、原 Manifest 和全部分片均在，可申请当前授权后打开验证游标或完整回放 |
| RetiredPendingSeal | 清理事务与墓碑已提交，清理事件尚在 outbox；材料不可再申请，尚无该清理事件的签名证明 |
| RetiredSealed | 清理事件已被正确身份封存；保留原签名根和清理记录，完整材料明确不可用 |
| Corrupt / Missing | 无合法墓碑或关联不符的缺片；属于完整性错误，不得自动解释为主动清理 |

PendingSeal／Sealed 应从同一清理事件的 outbox／签名覆盖关系派生，不另设一份可漂移的业务权威。Ready 不回写 Failed，也不能继续以“完整历史查询成功”隐式交付被清理结果。

默认 `query_with_operation` 在当前授权校验后检查材料状态：Complete 返回原结果；Retired 返回类型化 `MaterialsRetired`，让界面明确提示“此次筛选的回放材料已清理，可重新筛选”。按钮使用新 operation 查询最新来源。原响应仍保留，但只允许通过明确的历史结果查看接口读取，必须同时展示 `replay unavailable`，不能沿原成功接口悄悄回退，也不能以新查询补造旧证据。未知存储／传输错误仍保留原 operation 重试，不能误报已清理。

## 墓碑、CAS 与审计事件的具体合同

建议新增预编译 Protobuf＋LZ4 `ArchiveRetirement` 原件，建议单条原 PB 至多 16 KiB，身份字段沿用 256 字节规则；采用精确字段数、重复字段、版本、摘要长度和尾部检查。以下是候选字段，不是已生成 schema：

- `schema_version`、独立 `retirement_operation_id`、目标 `subject`、原 `operation_id`。
- 原 ReadObservation 原 PB 摘要及其完整容器摘要、`archive_root`、原 Manifest 完整容器摘要；不能只存调用方自报的 root。
- 原片数、原逻辑 Part 成本、原尾链，以及明确的 `all_parts` 清理范围。
- 清理政策 ID／版本／摘要、有限 reason code；可记录宿主观察时间，但不将它当作独立可信时间。
- 清理记录修订和预期上一条保留状态摘要；首期一个归档只允许一次 Complete→Retired，前态为空且修订为 1。

原 Manifest 与 ReadObservation 原件已经保留；墓碑不需要再次塞入它们。清理审批以目标库审计身份、目标 subject、原操作 ID、预期 root、预期材料修订及政策摘要为单位，不能用位置或“当前最新查询”代替。相同清理操作 ID 的精确重试返回原清理回执，并重新执行当前授权；同 ID 不同目标／政策、旧修订或错误 root 均拒绝。任何清理 API 都不得接受 guest 自报授权。

清理本身需要新的类型化审计事件。建议增设独立操作种类／schema，原事件继续保持现有 kind 4；新事件保留完整清理原件，引用旧读取事件及其 root。最终种类编号须先核对核心与 audit schema，不把这里的候选名称当作现有 wire 值。清理不能仅写诊断日志、独立 JSON 文件或没有永久操作索引的旁路账本。

## 单档原子提交与恢复顺序

建议的首个 API 形状为 `retire_read_archive(request, authorize) -> RetirementReceipt`，只在支持新格式的 Store 提供。请求包含独立清理 ID、目标、预期 root／材料修订及政策事实。返回 receipt 说明提交结果，不承诺已经封存、用户已收到或磁盘空间已经归还。

1. 在 IMMEDIATE 事务内读取目标、capture 状态、原观察、Manifest 和当前材料状态，检查全局 ID 占用、CAS、完整关联及当前政策。为首次退休完整核验原分片；不能替损坏归档补写合法清理说明。
2. 构造并固定清理原件，先确认永久身份记录、清理事件和 outbox 的容量足够。若容量不足，整个清理拒绝，不先删材料。应为清理终结预留独立小额元数据预算，避免“材料满了却无法记录清理”；预算耗尽依然不能无记录删除。
3. 同一事务写入清理原件、墓碑、材料状态链接、独立永久操作／事件索引及 outbox，删除目标全部 Part 行，并按真实前后逻辑成本更新派生账本。保留原 Manifest、原 root 链接、原 ReadObservation 和 capture 状态。更改这些旧摘要的行为一律拒绝。
4. 在最终提交位置调用当前授权回调，拒绝时所有删除与记录同时回滚。commit 失败返回 CommitUnknown，按清理操作 ID 查询；不能直接重复删除或将旧 Ready 改成 Failed。
5. 后续正常封存对清理原件签名。封存失败只保留 RetiredPendingSeal 并报告维护问题；不能重新放行旧查询、伪称清理已有签名，或把材料自动从当前库重新生成。

为保持 bounded 事务，首期只处理单档，仍受既有 65536 片／4 GiB 上界约束。批量用户操作逐档报告提交结果；不要把尚未提交的剩余清单声称全部完成。单事务 DELETE 的延迟和 WAL 增长必须实测；若需要分阶段物理清理，应另设计 `retirement scheduled` 与幂等删除进度，不能直接将部分删除套入本合同的 Complete／Retired。

## 审计验证与材料验证必须分开报告

验证器建议返回结构化的两个维度：`AuditChainStatus` 和 `MaterialStatus`。保留原读取原件和已签清理事件后，可以核对完整签名链、原 root、前后事件顺序和退休关联；由于分片已经不存在，不能再声称已核验其全部内容、源 census 或执行回放。

独立签名 Archive 原本只收集事件，未必携带分片。它验证签名链成功不能替代材料可用性检查。核心库完整性检查可以在新格式中接受**有合法、精确关联墓碑的整档缺片**，但必须显示是否仍等待清理事件封存；没有墓碑、错误 root、错误 owner／subject、缺失清理事件、部分残留和孤立材料均为错误。不能把所有 NotFound 改成“可能已清理”。

旧默认 CLI 不能在材料退休时仍打印含糊的整体 PASS。至少分别支持并报告：签名链核验、库结构／保留状态核验、完整材料要求、真实回放。要求完整材料或回放时，Retired 是明确的不可用结果和非成功退出码；不打印 MATCH、完整来源核验或完整证据通过。尚未封存的退休事件只能得到 pending 状态，不能扩大签名链覆盖范围。

## 游标并发与真实空间回收

现有 `ReadArchiveCursor` 拥有独立 WAL 只读事务，Store 被 Drop 后仍可继续读取。首期允许清理前已经成功准入的游标读完旧原件；这是固定快照的既有合同，不是权限撤销或立即擦除。新游标在自己的固定事务内核对材料状态、root 与清理链接，只能观察完整旧态或完整新态；Retired 拒绝准入，不得先从新墓碑接受 root，再从旧连接拼材料。

游标 `finish()` 仅确认 EOF，`close()`／Drop 才结束读事务。清理不能强制关闭别人的连接或制造过期切片。Windows Session 的应用租约仍独立存在，游标归零不代表可以启动第二个 Session。若将来需要清理等待所有读者，须新增真实跨连接读者登记／期限与异常退出合同；当前 owner Arc 不能充当全库持久读者名册。

事务删除后，逻辑用量可以下降，但旧读者、WAL、freelist、备份和导出可能仍保留物理字节。不得把逻辑账本减量报告为已释放多少真实磁盘。WAL checkpoint 与文件压缩是后续维护动作，应明确 busy／失败、可恢复重试和空间观察；不在清理写事务内等待读者退出或递归删除数据库文件。

## 全库配额与永久元数据的边界

本轮计划中的 DB14 账本涵盖 Preparing 和 published，按每份 Manifest 的原 PB＋完整容器以及所有 Part 的原 PB＋完整容器计费，包含 finalize 元数据增量；capture State 的独立费用、Evidence、ReadObservation 和 outbox 不在此归档账本内。两张派生表为 `read_archive_costs` 和 `read_archive_totals`，必须保持可重建，不成为业务原件的另一权威。清理阶段需要显式区分保留的 Manifest／墓碑／状态成本、仍可用 Part 成本和实际文件字节；每个成本变化与对应业务变更同事务提交。仅按现存 Part 行重算账本，不能因此把缺片误认成正常减量。

首期保留 Manifest 和完整 capture State，因此旧的档数／状态数限制可能仍然耗尽；删除 Part 只能回收对应逻辑字节。不得承诺靠 GC 自动解决 8192 档或 4096 状态上限。若下一步选择把“完整材料档数”与“永久身份／墓碑数”分开计费，必须显式升级计费合同并为永久元数据设置独立有界预算；旧全库计费不能静默漏掉 retired 目录。元数据额度不足时拒绝新查询，不能删除墓碑重用 ID。

同一个原操作 ID 在多个备份和恢复分支中仍表示同一历史意图。永久保留记录不可依赖当前清理策略、TTL 到期或 UI 最近查询列表；这些列表都不能成为全局 ID 去重权威。

## 备份、恢复与历史回退

新格式备份必须保留：原签名段与读取原件、原 Manifest、capture 状态、墓碑和清理原件、永久 ID／事件索引，以及尚未封存的清理事件。Complete 归档包含全部 Part；Retired 归档明确没有 Part。快照在同一数据库视图内导出，恢复时核对状态和材料闭包，再重建／核对派生账本。

恢复新快照不能自动从当前 guest catalog、别的工作区或网络补材料，不得恢复旧 grant。清理前的旧备份可能仍包含原件；其恢复是一个更早历史视图，不证明后来没有发生清理。现有身份租约阻止并发打开同身份副本，但不能独立阻止顺序回退；检测旧备份回退需要调用方保留较新的可信签名检查点。本方案不声称删除所有外部备份或阻止材料再次被复制。

首期不提供对 retired 记录的原地 rehydrate。后续若支持重新导入原件，必须核对完整原 root 和所有材料、重新记录可用性恢复事件，保留原退休事件，不能抹掉墓碑或重用原操作执行新查询。

## 实施顺序与验收门槛

1. 固定 Retirement 原件、材料状态、类型化读取结果及版本门禁；列出所有永久 ID 占用入口。旧格式只读仍验证旧完整闭包，新格式不得被旧验证器误接纳。
2. 同库实现单档退休事务、末次授权、CommitUnknown 查询、元数据预留及派生用量核对；包括旧超额库仍可受控清理、不为缺片库补墓碑。
3. 更新 `lookup_read`／`read_archive_manifest`／Part API／cursor 准入、capture Ready 验证、默认 query 和审计 CLI。不要先放行 DELETE 再等消费者升级。
4. 扩展签名与备份恢复资格：清理前后原读取原件／root／签名字节不变；清理事件实际 Ed25519 覆盖；源库与凭据删除后从备份正确区分 Complete、RetiredPendingSeal、RetiredSealed。
5. 实测并发 cursor 与清理事务的两种顺序，旧 reader 完整读完／新 reader 拒绝、close 后 WAL 回收；测实际文件大小，不用逻辑 ledger 数字代替。
6. 故障注入覆盖删除前后、墓碑／事件／账本写入、最后授权、提交前后和封存失败；验证重启后永不出现半片成功、ID 复用、旧 Ready 假成功或无签名清理被宣称已认证。

验收必须包含真实工作台多阶段查询及隔离 replay：Complete 材料真实重放 MATCH；清理后只能验证原审计关联并明确无法回放；修改保留记录、root、subject、事件链接或删除单片必须拒绝。上述资格尚待实现，本文件没有增加测试通过数量。
