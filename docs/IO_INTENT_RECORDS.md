# IO-C：意图记录与持久历史

状态：实验性记录格式已接入 Store v16 的原子历史提交、发送前后续意图/审计容量预留、现有签名审计队列和快照验证。尚未接入受保护 IO 原件、broker 当前实例绑定和实际后端；历史记录与预留都不能据此授权发送，也不是 SDK 稳定承诺。

## 格式与绑定

`core/schemas/io_intent.proto` 定义独立 Protobuf 记录，使用现有 LZ4 信封，magic 为 `MROWIOI1`、格式版本为 1，解压后最多 4096 字节。原始 Protobuf 的 SHA-256 用于前驱绑定。解码在分配字段前检查字段号、重复字段、线类型和长度，并要求重新编码与原字节一致；未知语义必须走显式版本升级。

同一 operationId 必须绑定完全相同的主体、包摘要、独立 IO 能力、协议摘要、原请求摘要、批准摘要、目标摘要、请求字节量和响应上限。摘要只引用历史材料，不证明原件已保存、目标已授权或批准仍有效。密钥、原始 URL、请求和响应正文不得写入这些摘要字段；原件由后续受保护证据层保存。

当前候选格式绑定当前实验性 IO schema 摘要及普通任务 16 MiB 上限。后续流式 profile、协议演进及旧历史读取需要版本分派，不能直接放宽旧格式或把此上限宣称为整个网络系统的上限。

## 状态与恢复含义

| 转换 | 修订 | 含义 |
| --- | --- | --- |
| 初始 → Prepared | 1 | 命令已构造；执行前仍需当前授权、容量预留和持久提交 |
| Prepared → OutcomeUnknown | 2 | 必须先提交这一边界，再接触后端；即使在提交后、发送前崩溃，也保守保留未知结果 |
| Prepared → CancelledBeforeDispatch | 2 | 仅适用于尚未跨越发送边界的取消 |
| OutcomeUnknown → Observed | 3 | 保存原响应或核对结果的摘要与来源，不等于远端业务成功 |

OutcomeUnknown 只允许核对，不能自动重发、换 operationId 重试或改称未发送。Observed 与 CancelledBeforeDispatch 为本记录的终态。超时、断连、取消和 GET 方法都不能证明外部效果不存在。

`Record::decode` 只验证单条记录的格式与语义。`verify_successor` 另校验完整命令、修订递增及准确前驱摘要；即使两者通过，也仍需权威 Store 中的实际前驱、原子比较并交换与签名审计，才能建立可信历史；这些存储与审计入口现已接通。历史批准摘要不会恢复为 live grant。

## Store v16 与预留

`io_intents` 将稳定命令 ID、修订与永久事件 ID 关联；事件原件仍放在现有 `operations`，新对象种类为 5。每个修订的事件 ID 为 `io-event-` 加域分离 SHA-256，输入是原始记录摘要。命令 ID 不变，事件 ID 各不相同，因此三次状态提交不会覆盖同一审计事件。

`append_io_intent_local_authorized` 在同一即时写事务中校验原始命令和准确前驱，检查普通操作、读取准备和其他意图的 ID 占用，经全局预算入口检查本次 outbox 容量（扣除全部在持预留），原子追加历史、原件和事件序号，并在提交前调用当前授权检查。精确重试返回已保存的那个修订，保留其原始压缩字节，不生成新事件；即使它是旧 Prepared，也不能解释为最新状态或重发许可。查询最新状态使用 `lookup_io_intent`。

发送边界（Prepared → OutcomeUnknown）前必须先通过 `reserve_io_intent_followup` 为同一命令建立完整后续预留：恰好 1 个事件、最多一个记录信封（4240 字节），由 `io_reservations` 表持久持有并计入所有 outbox 写入口（普通内容、配置记录、读取观察、归档发布和意图追加）的可用额度，其他写入无法挤占；相同 operationId 幂等不重复扣减，不同命令拒绝，授权失败原子回滚，Prepared 阶段可用 `release_io_intent_followup` 释放，发送前取消自动释放，终态 Observed 在同一事务中消费自身预留（此后即使以更小预算重开也保证可写观察）；重开或崩溃后预留不丢失、不重复恢复，完整性闭包要求 OutcomeUnknown 必有预留、终态必无预留。预留是 Store 内的逻辑配额，不是物理磁盘空间保证：SQLite 真实满盘仍以 StorageFull 报告；预算是每次打开的配置而非持久额度，已成立预留不因预算调小而失效，仅对同一事件量有效。v15 到 v16 显式迁移新增空表，不重写旧内容或旧事件；旧版本的库若混入新表则拒绝，不静默修复。较旧程序不能读取 v16，测试阶段的数据库升级应使用备份和隔离验收。

打开、只读审计验证、待签名队列、卡片快照和全库快照均识别新格式；历史与种类 5 事件双向核对，逐修订验证前驱和事件顺序，预留状态参与同一完整性检查。签名封存复用原件和既有链，封存不掉落在持预留。

## 后续必须贯通的实现

1. 接入受保护请求／响应材料、录制与证据保留策略，并把受保护原件容量纳入发送前预留（当前预留只覆盖后续意图修订及其审计事件）。摘要或签名不证明材料存在、远端成功或用户收到响应；缺材料明确报告 EvidenceUnavailable。
2. Broker 核实当前实例、撤权、期限和共享预算，绑定唯一活跃执行；持久记录、预留和历史批准摘要不能作为 live grant。
3. 继续验证实际后端的效果／结果间隙：既有真实子进程退出验证只覆盖 SQLite 提交与迁移，不证明 HTTP 服务或外部文件的效果恢复。
4. 接入实际文件操作与双向网络服务，并推进 C／C++／Rust SDK、授权 UI、独立重放和各平台资格测试。
