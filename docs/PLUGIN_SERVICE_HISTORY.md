# 入站服务的持久请求与恢复

状态：Windows 本机持久请求／结果恢复子集验证通过（PASS_SCOPED），见 [验证报告](../reports/service-history-2026-09-19.md)。本文对应原生宿主显式发布的 [受管服务](PLUGIN_MANAGED_SERVICE.md)，不等同持久发布界面、完整业务事务或新版三语言 SDK 已完成。

## 路由与请求身份

`ServiceHost::durable_route` 在原发布批准之外，接受宿主固定的 `ServiceJournal`。该 journal 包含非零 32 字节 namespace、1毫秒至30天的结果保留期限和可信 UTC 毫秒时钟。namespace 必须由宿主为同一服务持续保存，重启不得重新随机生成；更换 namespace 是新的请求身份空间，不是旧请求恢复。时钟必须纯粹、有界、不能重入 journal 或执行器，并应在重启间保持可信 UTC。

持久路由要求恰好一个 `Idempotency-Key`，长度1至128字节、仅可见 ASCII。重复、缺失、过长以及被 Connection 指定为逐跳字段的 key 拒绝。认证后才访问历史。key 从 guest 业务头中移除，仅保存其 SHA-256；key 不是认证或内容权限。

外部幂等身份绑定 namespace、宿主确认的 principal、service 和 key。方法、目标、正文、业务头及内部 handler 不用于生成新的操作 ID，而是在完整请求匹配中检查。因此同 key 改输入或更换处理器会冲突，不会获得新的执行机会。包摘要和保留策略也必须与原命令相符；包升级不会借旧 key 自动再执行。

业务头按小写名称稳定排序，同名多值的相对次序保留；HTTP解析后的值、查询顺序和正文原字节继续参与精确匹配。认证、Cookie、代理、连接及分帧字段被剥离，不能把换 token 当作新业务输入。当前原生请求头仍是严格文本路径。

## 一个权威存储与唯一执行边界

没有新建旁路数据库。`RequestRecord` 是严格 Protobuf＋LZ4，保存 namespace、key 摘要、初始 UTC／截止时间、保留期限及原服务 Cap’n Proto 帧；随后作为现有受保护材料进入原 HostRuntime 的 Store。原有 IO 意图、事件、材料容量和恢复机制继续生效，不创建另一套业务真相。

1. 在一个 SQLite Immediate 事务中，原子写入 Prepared、后续事件容量、请求／响应材料容量及请求原件；任何授权失败、容量不足、错误或提交前退出均回滚，不能留下没有请求原件的新 Prepared。
2. 原实例授权与请求有效期再次通过后，用严格的唯一 claim 提交 OutcomeUnknown。只有得到此次新提交成功的调用者可以进入 guest；重复历史 append 的成功不能替代 claim。
3. 执行仍使用原 IoWorker 和已绑定发布／监听许可。每次外发仍需独立端点批准，并走 Broker；Broker 自己的外发边界也使用唯一 claim。
4. 有效服务完成帧先保留原件、再提交 Observed，随后才允许网络交付。若中间出错，历史保持待核对，不能根据缺少 HTTP 响应推断没有执行。

claim 已提交但进程尚未真正进入 guest 就退出，仍属于 Unknown。这种保守分类避免自动重做副作用，不宣称网络系统可以保证端到端“恰好一次”。SQLite 提交结果不明时同样不能当作执行许可。

## 重试、到期与撤权

- 同 key、同请求、完整 Observed 原件：在重新鉴权、重新检查当前包／实例／发布／监听批准后返回保存结果，跳过 Wasm。响应仍计入本次共享字节预算，队列与 job 额度也不绕过。
- 同 key、不同输入／包／策略／处理器：409冲突。
- 已跨执行边界且尚无完整观察：409待核对，绝不自动执行第二遍。
- 结果保留期限已到：410，不交付结果，也不删除历史或重新开放该 key。
- 材料缺失、完整性不符或存储不可用：拒绝成功交付；不降级为无记录执行。既有损坏历史不能用本次输入猜造原件。

UTC高水位在同journal的所有clone间共享，回退拒绝；原记录的created/expires在重启后仍保留。跨进程持久时钟高水位与可信时间服务尚未实现，宿主须保证重启间 UTC 可信。

期限参与运行边界与实际外发检查：认领后把剩余时间并入原作业的单调deadline；guest启动、每次import、真正backend调用、HTTP监控和Ready/read均重新检查UTC。排队、回包和重试不续期。这里不是实时抢占：连续 guest 计算仍由 fuel 限额约束，deadline 在执行边界检查。撤权只阻止后续操作与交付，无法追回已经传出的字节或撤销上游已发生的业务效果。

新鲜请求和恢复请求都重新检查实际 principal 的 service scope。缓存与task ID均不是授权；service scope 不是内容权限。内容型路由另将有效内容范围摘要绑定原请求，并在重放时检查当前逐对象授权，见 [内容权限交集](PLUGIN_SERVICE_CONTENT.md)。普通 `route` 保留不使用幂等键的有限服务入口，宿主必须为需要副作用恢复的API明确选择durable路由。
